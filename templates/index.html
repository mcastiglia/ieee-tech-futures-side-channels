Power Analysis for Password Bypass

Live side-channel attack demo · Dr. Mike Borowczak · Design of Resilient Architectures for Computing

THE IDEA A correct vs. incorrect character causes a different code path, which draws different amounts of power — a measurable signal we can read from outside the chip.
THE ATTACK Capture power traces for every candidate character. The outlier trace reveals the correct one. Repeat this one position at a time to recover the full password.
THE THREAT Embedded systems, smart cards, IoT devices, secure enclaves — any hardware that checks secrets in software is potentially vulnerable.

STEP 1

🔧 Hardware Setup

The ChipWhisperer scope is a USB oscilloscope specially designed for power analysis. It clamps onto the target board’s power rail via a shunt resistor and records thousands of voltage samples per clock cycle.

The target firmware (basic-passwdcheck) implements a character-by-character password comparison that returns immediately when a wrong character is found — an early-exit or short-circuit comparison. This is the vulnerability we exploit: more correct characters → more loop iterations → measurably more power consumed.

This step connects to the scope over USB, compiles the firmware with make for the correct platform, flashes the resulting .hex via the scope’s built-in programmer, and runs a sanity capture to confirm {{ max_samples }} samples come back cleanly. 


      


      
      

        
STEP 2

        
👁 Compare: Correct vs. Incorrect


        

          

            Before running a full attack we first confirm the leakage exists. We capture
            one power trace for a character we know is correct at position 0, and one for a
            character we know is wrong, then overlay them.
          

          

            The two traces will look nearly identical at the start — the MCU receives our
            byte and begins the comparison. Then they diverge. The correct
            character causes the firmware to advance to the next comparison iteration, drawing
            power for longer. The wrong character causes an immediate early exit, cutting the
            trace short.
          

        


        

          🔍
          
WATCH FOR: The traces track together, then split apart.
          That divergence point is the branch instruction that separates a correct character from
          a wrong one.

        


        

          
          
          
        

        

        

      


      
      

        
STEP 3

        
🔎 Sweep All Candidates


        

          

            Now we do this systematically: capture one trace per candidate character
            (a–z, 0–9) and overlay all 36 at once.
          

          

            Known prefix is the portion of the password already cracked. On
            the first run it is empty (we are guessing position 0). After cracking character 1
            you would enter it here so the firmware advances past it before hitting the unknown
            position.
          

          

            Samples to plot controls how much of each trace is rendered.
            More samples show more of the execution; fewer samples zoom in on the early
            divergence window and run faster.
          

        


        

          🔍
          
WATCH FOR: 35 traces cluster tightly together. One trace breaks
          away from the pack — that outlier is the correct character at the current
          position.

        


        

          
          
          
        

        

        

      


      
      

        
STEP 4

        
📉 Difference Traces


        

          

            Overlaid raw traces can be noisy and hard to read. We sharpen the signal by
            subtracting a baseline from every candidate trace.
          

          

            The baseline is captured using \x01 (ASCII 1, not a valid password
            character), which guarantees the firmware rejects it at the very first comparison.
            This gives us the shortest possible execution path as a reference —
            zero correct characters, minimum power.
          

          

            Subtracting this reference from each candidate trace cancels out noise that is common
            to all traces (power supply ripple, clock harmonics, USB interference) and leaves only
            the extra power drawn by extra comparison work. A spike in the difference trace at a
            particular time offset is the firmware spending more cycles — pointing directly
            at the correct character.
          

        


        

          📉
          
WATCH FOR: Most difference traces stay flat near zero. The correct
          character shows a prominent spike above the noise floor — that spike is the
          firmware doing one extra comparison iteration.

        


        

          
          
          
        

        

        

      


      
      

        
STEP 5

        
📊 Quantify: SAD Scores


        

          

            Reading the “biggest spike” off a plot by eye does not scale. We need a
            number. We use SAD — Sum of Absolute Differences:
          

          
SAD(candidate) = Σ | trace[i] − reference[i] |   for all sample points i

          

            A high SAD score means the candidate trace deviates a lot from the “always
            wrong” reference. The character with the highest SAD score is the
            best guess for the current position because it caused the most extra work inside
            the firmware.
          

        


        

          💡
          
KEY INSIGHT: We take the absolute value before summing.
          Without it, positive and negative differences could cancel each other out and wash away
          the signal. Absolute value ensures we measure total deviation, not net
          deviation.

        


        

          
          
        

        

        

        

      


      
      

        
STEP 6

        
🚀 Full Automated Attack


        

          

            Steps 2–5 are repeated automatically for every position in the password.
            At each position the attack:
          

          
    
            
  1. Captures a \x01 reference trace (firmware rejects at current depth).
    2. 
            
  2. Sweeps all 36 candidate characters, computing a SAD score for each.
    3. 
            
  3. Picks the highest-scoring character as the correct one and appends it to the
            recovered prefix.
    4. 
            
  4. Moves to the next position with the updated prefix and repeats.
    5. 
          

          

            The total number of captures is length × (36 + 1) —
            one reference plus 36 candidates per position. For a 5-character password that is
            185 captures, compared to up to 365 = 60 million brute-force guesses.
          

        


        

          ⏱
          
LIVE: The password will appear one character at a time as each
          position is cracked. Watch the SAD scores shift as the known prefix grows and the
          firmware advances deeper into its comparison loop.

        


        

          
          
        

        

        

        

      


      
      

        
💬 Discussion


        

          

            This demo targets a deliberately vulnerable firmware. Real-world embedded systems
            often contain the same class of bug because developers write natural, readable code
            without considering physical side channels.
          

        


        

          

            
What made this attack possible?

            
The firmware used an early-exit comparison: it
            returns the moment a wrong character is found. This means each additional correct
            character causes one more loop iteration, consuming measurably more power and
            time. The side channel is the variation in execution length.

          


          

            
How would you defend against it?

            
Use a constant-time comparison that always
            iterates through every character regardless of correctness, so execution length
            does not depend on the secret. Additional countermeasures include power-rail noise
            injection, randomized execution delays, and masking (randomizing intermediate
            values).

          


          

            
What other systems check secrets character-by-character?

            
PIN pads, smart cards (EMV), secure boot verification, HMAC
            comparison in TLS handshakes, API key validation in microcontrollers. Many
            cryptographic libraries historically used strcmp() for secret
            comparison — a classic constant-time bug.

          


          

            
Could you use this technique on AES?

            
Yes — this is called Differential Power Analysis
            (DPA), pioneered by Paul Kocher in 1998. Instead of comparing full traces,
            DPA uses statistical correlation between power samples and a model of internal
            computations (e.g., the S-box output). It can recover AES-128 keys with ~1000
            traces.

          


          

            
Is this attack limited to password checks?

            
No. Any computation whose power consumption or timing correlates
            with secret data is vulnerable. This includes RSA (via square-and-multiply),
            elliptic curve scalar multiplication, and even cache-timing attacks on software
            running on full CPUs (Spectre, Meltdown share the same conceptual root).

          


          

            
What does “side channel” mean exactly?

            
A side channel is any unintended information path that leaks
            data about a computation — power consumption, execution time, electromagnetic
            emission, acoustic noise, even cache access patterns. Side-channel attacks exploit
            the physics of the implementation, not a flaw in the algorithm itself.
